## 0. The finding that matters more than everything else combined

Two separate fresh testers, on two separate days, typed their own unscripted scam/walkaway messages into the real chat input. **Trust Shield fired on 0 of 4+ organic attempts across two listings. It only fires on the exact phrase published, with a copy button, on the app's own "Demo Script" page.** That is not a UI bug — it is proof the mechanism is a string/keyword match against one or two known phrases, not a real AI classifier, despite the pitch claiming otherwise. Hot-Lead Radar is partially real (fired 1 of 4 organic walkaway attempts) but still unreliable. A judge who does the single most obvious adversarial thing — type their own test message — will watch the signature feature fail, live, in front of them. This is fatal to both the 50%-weighted Completeness/UX score and the 30%-weighted Innovation score, because it's a gap between a claimed capability and an observed one, which reads worse to a judge than a smaller, honestly-scoped claim ever would.

**This is the only thing that decides whether this submission can win. Fix it before touching anything else in this document.**

## 1. P0 — Make Trust Shield and Hot-Lead Radar real, not scripted

1. Find every code path that can flag a message or move the risk meters. If any of them matches against a hardcoded string, a fixed phrase list, or a specific demo-message ID, delete that path entirely — it must not exist as a parallel/fallback mechanism once the real one is in place, or the next adversarial tester will find the same seam.
2. Wire a single real classifier call (Groq, one few-shot prompt, one call per inbound message) into the actual message-send handler used by the real chat input — the same one the user types into, not a separate "demo" handler. Contract: `{trust_flag: bool, trust_reason: string|null, lead_score: 0-100, risk_of_loss: 0-100}`.
3. Tune the system prompt with several *paraphrased* examples of each pattern, not just the one scripted sentence — advance payment via any named payment method (UPI, Zelle, Venmo, Bitcoin, wire transfer, "cash now"), any phrasing of "skip the in-person viewing," any phrasing of walking away/losing interest/found something else. The goal is generalization, not a longer keyword list — if your fix is "add more strings to match," you have not fixed the actual bug.
4. Adversarially test it yourself before calling this done: from at least 2 different listings, type at least 5 different scam-intent phrasings you invent fresh (not from this document) and at least 5 different walkaway-intent phrasings. Every single one must correctly flag or escalate. Also re-confirm a clearly benign message still produces zero false positives (already verified working — don't regress it).
5. Once this is solid, **flip the weakness into the proof**: update the Demo Script page and the demo video plan to explicitly invite the viewer/judge to type their own test message live, instead of only offering the two scripted buttons. This turns the exact thing two judges used to break the app into the moment that proves it's real — and it is a far more memorable demo beat than a canned button click.

## 2. P1 — fix once P0 is solid, in this order

### 2.1 The Guardian Copilot Radar panel is completely invisible on mobile
The Lead Readiness / Walkaway Risk / Trust Shield Status sidebar — the product's entire headline feature — collapses to a 0×0 element on a ~390px viewport. A mobile user or judge sees only chat bubbles and buttons, never the AI scoring the whole pitch is built on. Fix the responsive layout so this panel renders (even as a collapsible drawer or a section below the chat) on mobile. This is as serious as the P0 for anyone who opens the link on a phone, which is likely for real-traction testers.

### 2.2 Role switching doesn't actually switch conversations
Clicking "Seller (Elena)" or "Seller (Marcus)" only changes the input placeholder name — it does not switch you into that seller's own listing/thread, so you stay typing "as Elena" inside Priya's Glasshouse conversation. Fix so selecting a seller role actually loads that seller's own active listing/conversation.

### 2.3 Listing cards aren't clickable
Only the small "Chat with Seller" button inside each card works — the photo and title have no `href`/`onClick`. Make the whole card clickable through to the chat (keep the explicit button too, but don't make it the only entry point).

### 2.4 No escalation dedup/cooldown
Re-triggering Hot-Lead Radar on an already-escalated thread stacks duplicate system messages and duplicate Agent Radar cards (observed inflating the badge count to 13 in testing). Add a simple guard: one active escalation per thread; re-triggers update the existing one instead of creating a new one.

### 2.5 Audio race condition — mostly fixed, still breaks under stress
Single, isolated Play clicks now pass reliably (7/7 in clean testing). It still fails under rapid/overlapping interaction: multiple escalations triggered in quick succession, or clicking Play on more than one card back to back. Add a request lock/queue so a new escalation or play action can't interrupt an in-flight audio load, and re-test specifically under that stress pattern (not just one-at-a-time), since that's exactly where it still breaks.
